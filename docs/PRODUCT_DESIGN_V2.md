# ReviewOps 产品设计文档 v2

基于「存量初始化 + 定时巡检 + 按需拉取 + 单条归因」的产品设想，本文档约定：**产品架构、数据来源与流向、统计口径、用户地图**，作为后续编码的统一依据。**不涉及具体代码实现**，仅做设计与口径定稿。

---

## 一、产品定位与核心场景

| 场景 | 说明 | 对应能力 |
|------|------|----------|
| **每日晨会看板** | 模拟「过去一天工单」的统计与结论；工单实时产生，系统在**固定时间点**拉取并分析，看板展示该次（或最近一次）分析结果 | 存量初始化 + 定时任务结果展示 |
| **定时任务演示** | 向面试官/客户展示：从哪拉数据、新增多少、高危多少、如何分诊与行动 | 「运行智能工作流」按钮 + 下方执行过程与日志 |
| **按需拉取** | 例如上午发版后 Jira 激增，PM 到平台主动跑一次工作流，看新工单归因 | 同上按钮，数据源为当前可拉取的新增工单 |
| **单条归因** | 产研发现一条疑似高优工单，只对这一条做 RAG+ 分诊，不跑全量 | 单条归因实验室 + 「测试数据 / 真实数据」配置 |

## 二、数据来源与流向（统一约定）

### 2.1 数据源角色

| 数据源 | 角色 | 使用时机 |
|--------|------|----------|
| **test_tickets.csv** | **存量/初始化数据** | 仅当 DB 中**没有任何已分析工单**时，在 App 首次启动（或首次进入看板）时读入并跑一遍分析，结果写入 DB，看板展示该结果 |
| **test_tickets_incremental.csv** | **增量数据（定时/按需）** | 每次点击「运行智能工作流」时，从此文件按序或随机拉取一批（如 5–8 条）**未入库**工单，入库并跑分析，结果写入 DB |
| **单条输入（文本框）** | **单条归因** | 用户在「单条归因实验室」输入一条工单内容，可选择：仅本次展示（测试数据）或 写入正式 tickets 表（真实数据） |

### 2.2 数据流向总图

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                            数据流向（概念）                                   │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  [ 首次启动 & DB 无已分析数据 ]                                               │
│       test_tickets.csv ──► 读入 ──► 写入 tickets ──► 跑工作流 ──► 写回       │
│       (存量)                    (未处理)           (rag_result/action_plan)   │
│                                       │                                      │
│                                       ▼                                      │
│                               看板展示 = 该次分析结果（模拟「过去一天」）      │
│                                                                             │
│  [ 定时任务 / 按需执行 ]                                                      │
│       test_tickets_incremental.csv ──► 拉取 N 条未入库 ──► 入库 ──► 工作流  │
│                                       │                                      │
│                                       ▼                                      │
│                               看板可更新为「最近一次巡检结果」或保持「昨日」   │
│                               执行过程在「运行智能工作流」下方展示             │
│                                                                             │
│  [ 单条归因 ]                                                                │
│       用户输入一条 ──► RAG + 分诊 ──► 仅展示 或 写入 tickets（由配置决定）    │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 2.3 关键口径约定

- **存量初始化**：只做一次。判断条件建议：DB 中不存在「已处理」的工单（或 tickets 表为空）。通过后：读 test_tickets.csv → 批量 insert（状态为未处理）→ 触发一次工作流（或等价分析）→ 写回 rag_result / action_plan，并标记为已处理。
- **定时/按需**：每次点击「运行智能工作流」从 test_tickets_incremental.csv 拉取一批**未在 DB 中存在的 ticket_id**，入库后跑同一套工作流，结果写回 DB；下方 UI 展示：数据来源、本批条数、高危数、各节点产出等。
- **单条归因**：不经过 monitor 节点；输入内容直接进 RAG + agent + 行动节点。若用户选择「真实数据」，则写入 tickets 表（并建议标记来源为 single_ticket / is_test=0）；若「测试数据」，则不写表或写到一个单独的「测试工单」存储（或仅内存展示）。

## 三、统计口径（看板展示什么）

### 3.1 看板统计的「时间范围」

- **建议口径**：看板展示的是**「最近一次完整分析」**所覆盖的工单集合的统计结果，用于模拟「过去一天」。
  - **首次启动后**：即存量初始化那批工单的统计（= 模拟昨天一天的工单）。
  - **之后**：可选择两种策略之一（产品定稿时二选一）：
    - **A**：看板始终展示「存量那一批」的统计，不随后续按需/定时运行而改变（强调「晨会固定看昨日」）。
    - **B**：看板展示「最近一次成功执行的工作流所覆盖的工单」的统计（存量初始化算第一次，之后每次运行智能工作流会更新「最近一次」）。
- **指标定义保持不变**：工单总数 = 该批数量；L1 拦截率 = 该批中未转研发占比；P0 升级率 = 该批中转研发占比。分子分母均限定在「该批」内，且仅统计**已处理**（有 rag_result/action_plan）的工单。

### 3.2 指标与数据来源（定稿）

| 指标 | 口径 | 数据来源 |
|------|------|----------|
| 工单总数（看板） | 参与「最近一次完整分析」的工单数（或存量批次的工单数，见上） | 从 DB 按「看板批次」或「已处理 + 归属该次分析」统计 |
| L1 智能拦截率 | 该批内 action_type 为 Email/ Escalate 或 category 技术支援 的条数 / 该批已处理条数 × 100% | DB tickets 表，action_plan / category |
| P0 研发升级率 | 该批内 action_type 为 Jira 或 category 研发升级 的条数 / 该批已处理条数 × 100% | 同上 |
| AI 技术简报 | 基于**同一批**工单的 rag_result / action_plan / diagnosis 聚合生成（非固定模板） | DB 中该批的 rag_result、action_plan、diagnosis_category 等 |

为支持「该批」和「最近一次分析」，需要在数据模型上能区分：哪些工单属于「存量批次」、哪些属于「某次定时/按需运行」。见下节 DB 设计。

## 四、数据库与状态设计建议（新增字段）

在现有 **tickets** 表基础上，建议新增或明确以下字段，以支撑「是否处理过」「读入时间」「批次」「单条测试/真实」等语义。

| 字段建议名 | 类型 | 含义 | 用途 |
|------------|------|------|------|
| **processed_at** | TIMESTAMP NULL | 该工单完成分析（写入 rag_result/action_plan）的时间 | 是否已处理、按时间范围统计「昨日」等 |
| **synced_at** | TIMESTAMP | 工单从外部源「读入」系统的时间（入库时间或文件拉取时间） | 区分「何时进来的」，用于「过去一天」的时间口径 |
| **batch_id** 或 **run_id** | TEXT NULL | 所属批次（如存量=init，每次运行智能工作流=run_ts 或 uuid） | 看板只统计「某一批」；历史按批次/按 run 展示 |
| **is_test** | INTEGER/BOOLEAN | 0=真实工单（参与看板统计），1=测试数据（单条归因且用户选测试） | 单条归因「是否入真实库」；看板与报表排除 is_test=1 |
| **source**（已有） | TEXT | 扩展枚举：stock_init | incremental | single_ticket | 便于区分来源与统计 |

**最小可行**：若暂不做「按批」统计，可先加 **processed_at**（NULL=未处理）、**synced_at**（读入时间）、**is_test**（单条归因用）；后续再加 batch_id/run_id 支持多批次看板。

## 五、用户地图与页面结构建议

### 5.1 用户角色（简化）

| 角色 | 目标 | 主要使用功能 |
|------|------|--------------|
| **晨会参与者（PM/研发/支持）** | 看「过去一天」工单的整体情况与结论 | 看板（指标 + AI 简报 + 可选列表/明细） |
| **运维/支持** | 触发定时或按需拉取、看执行过程与结果 | 智能工作流页：点击运行、看日志与本次结果 |
| **产研/测试** | 对单条工单做归因、验证规则或模型 | 单条归因实验室；需明确「测试数据 / 真实数据」 |

### 5.2 多页面结构建议（从「单页多 Tab」升级）

当前为单页 + 两 Tab（智能巡检控制台、单条归因实验室），建议拆成**多页**，更接近成熟产品：

| 页面 | 路由/入口 | 内容要点 |
|------|------------|----------|
| **1. 数据看板（首页）** | `/` 或「看板」 | 仅展示：存量（或最近一次分析）的指标卡 + AI 技术简报 + 可选「本批工单列表」折叠；不放置「运行工作流」按钮，保持「结果页」纯粹 |
| **2. 智能巡检** | 「智能巡检」或 `/patrol` | 「运行智能工作流」按钮 + 执行过程（数据来源、新增数、高危数、各节点日志）+ 本次运行结果（Hero）+ 历史运行列表（按 run_id 或时间）；数据源说明：当前从 test_tickets_incremental 拉取 |
| **3. 单条归因实验室** | 「单条归因」或 `/playground` | 输入框 + 「测试数据 / 真实数据」单选项 + 执行归因 + 展示 RAG + 行动建议；若选真实数据则写入 tickets 并标记 is_test=0、source=single_ticket |
| **4. 设置/配置（可选）** | 「设置」或 `/settings` | API Key、数据源路径、单条归因默认「测试/真实」、是否自动做存量初始化等；侧栏可保留部分全局配置 |

这样：**看板 = 只看结果**；**智能巡检 = 只看执行与批次结果**；**单条归因 = 只做单条与测试/真实区分**；**设置 = 统一配置**。

### 5.3 与现有结构的对应关系

- 当前「数据概览 + 简报」→ 迁到 **数据看板（首页）**，数据口径改为「存量或最近一次分析批」。
- 当前「智能巡检控制台」Tab → 独立成 **智能巡检** 页，保留运行按钮 + 下方执行过程 + Hero + 历史。
- 当前「单条归因实验室」Tab → 独立成 **单条归因实验室** 页，并增加「测试数据 / 真实数据」配置与写入逻辑（见上）。
- 侧边栏「数据源、最后更新、API Key」→ 可保留在每页侧栏，或集中到 **设置** 页。

## 六、存量初始化与「首次启动」流程（逻辑约定）

1. **触发条件**：App 启动（或首次打开看板）时，检测 DB 中是否存在**已处理**工单（如 `processed_at IS NOT NULL` 或 tickets 表为空）。
2. **若未初始化**：  
   - 从 test_tickets.csv 读入全部工单；  
   - 写入 tickets 表，`source=stock_init`，`synced_at=当前时间`，`processed_at=NULL`，`is_test=0`；  
   - 对该批工单执行**一次**完整工作流（monitor 可跳过，直接使用刚入库的 id 列表走 filter → RAG → agent → action）；  
   - 写回 rag_result、action_plan，并更新 `processed_at`、可选 `batch_id=init`。  
3. **若已初始化**：不再自动读 test_tickets.csv；看板直接按「存量批」或「最近一次 run」统计（由产品策略 A/B 定）。

**注意**：存量初始化时可不经过「从 CSV 随机取 5–8 条」的 monitor 逻辑，而是「整批存量一次性入库并跑一次分析」，以符合「过去一天工单」的模拟。

## 七、单条归因「测试 / 真实数据」行为约定

| 用户选择 | 行为 |
|----------|------|
| **测试数据** | 仅在前端展示 RAG + 行动建议；不写入 tickets 表（或写入时 is_test=1，且看板与报表统计排除此类） |
| **真实数据** | 写入 tickets 表：ticket_id 可生成（如 single_ts_uuid），ticket_content=用户输入，source=single_ticket，is_test=0，synced_at=now，跑完分析后写 rag_result/action_plan、processed_at；参与后续看板统计（若看板采用「最近一次」策略则可能纳入） |

产品上需明确：单条「真实数据」是否参与「看板批次」统计（例如仅参与「工单总数」但不参与「昨日」批次），建议默认单条归因写入的工单**不**计入「晨会看板」的批次，仅计入「全部工单」或单独查询，避免混淆。

## 八、修改建议汇总（定稿清单）

| 维度 | 建议 |
|------|------|
| **产品架构** | 单页改为多页：数据看板（首页）、智能巡检、单条归因实验室、设置（可选）；侧栏保留全局入口与 API 配置。 |
| **数据来源与流向** | 存量 = test_tickets.csv，仅首次无已分析数据时读入并跑一次分析；增量 = test_tickets_incremental.csv，仅在「运行智能工作流」时按批拉取；单条 = 用户输入，按配置决定是否写入 tickets 及 is_test。 |
| **统计口径** | 看板 = 「存量批」或「最近一次完整分析批」的统计；指标仅针对该批已处理工单；AI 简报基于该批 DB 数据聚合，非固定模板。 |
| **DB 表** | tickets 表新增：processed_at、synced_at、is_test；可选 batch_id/run_id；source 枚举包含 stock_init | incremental | single_ticket。 |
| **用户地图** | 晨会看板用户 → 只看首页；运维/支持 → 智能巡检页执行与查看；产研 → 单条归因 + 测试/真实开关。 |
| **存量初始化** | 首次启动且无已处理数据时：读 test_tickets.csv → 入库 → 跑一次工作流 → 写回分析结果并设 processed_at。 |
| **单条归因** | 增加「测试数据 / 真实数据」配置；真实数据写入 tickets 并标记 source、is_test=0；是否计入看板批次由产品规则明确。 |

---

以上为产品架构、数据来源与流向、统计口径与用户地图的定稿建议；实现时可按此文档分步编码（先 DB 与口径，再多页与存量初始化，最后单条测试/真实与看板策略）。
